What's explicitly NOT here yet

Loops, addressable memory, RISC-V compatibility, formal verification, fuzzing, external audits, a second real proving backend, trustless on-chain verification (today's AttestedVerifier is a documented trust bridge, not a cryptographic verifier). See docs/ROADMAP.md for the full list.

Suggested Next Slice

In order of validation value

This is the actual order in docs/ROADMAP.md — not a fixed calendar. Each step only starts once the previous one is solid.

Next Not started

Loops

  • → A dynamically-sized execution trace (bounded, padded/truncated by actual run length) so JZ/JNZ can jump backward
  • → The "verifier re-executes and asserts everything" trick still works — the verifier can just run the loop itself
  • → Real design needed for trace-length selection and the resulting proof-size variability
After loops

Addressable memory

  • → Dynamic addresses (e.g. LD r0, [r1]), distinct from today's 4 static register slots
  • → Open question: does the no-secret-witness trick still hold, or is a real lookup/permutation argument needed?
Only after 1–2 are solid

RV32I compatibility

  • → Considered explicitly out of order — not worth attempting before loops and memory are real

Quality Constraints

The actual working discipline for this repo — see CONTRIBUTING.md.

1. Verify Every External API

Never assume. Read the crate source at the exact version tag, or run a minimal repro before writing production code.

2. No Stubs or Mocks

No todo!(), no return true stubs, no component named after a real product it doesn't implement. If something isn't built, it's in ROADMAP.md.

3. Honest Scope Docs

docs/ROADMAP.md and docs/HOST_SERVICE.md list what's real and what's not. Every gap is named with what it actually takes to close. No "coming soon."

4. Test Under --release

Winterfell's debug-mode degree check is over-strict for data-dependent constraint degrees (confirmed: not a soundness bug — see the code comment in zkvm-stark/src/lib.rs).

5. No Fabricated Specificity

If you cite a paper, a date, a benchmark, or a project name, it must be verifiable. Unverifiable numbers are not acceptable — see the "measured" tag on every metric on this page.
