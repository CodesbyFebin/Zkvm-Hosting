# What a real on-chain STARK verifier requires

[`contracts/`](../contracts) has a working, tested `ProofOrchestrator` — but it
delegates every accept/reject decision to a pluggable `IProofVerifier`, and the only
two implementations that exist are:

- `UnimplementedStarkVerifier` — reverts, always. Honest about doing nothing.
- `AttestedVerifier` — a trusted party (a service running `zkvm verify` off-chain)
  attests off-chain that a proof was checked. This is a **trust bridge, not a
  cryptographic verifier** — it moves trust from "the EVM checked the math" to "you
  trust this one key." It's a legitimate way to build and test the rest of the
  system today, but it must never be described as trustless.

This doc is about the gap between those two: what would it actually take to make
`verify()` check a real Winterfell STARK proof on-chain, with no trusted party at all.

## The pieces, in the order the verifier needs them

1. **Recompute Fiat-Shamir randomness.** The verifier re-derives every random
   challenge the prover used, by hashing the same transcript (commitments, public
   inputs) in the same order the prover did. This is why the *choice of hash
   function matters enormously* for an on-chain verifier:
   - Our current prover uses `Blake3_256` (see `zkvm-stark`'s `Hasher` type). Blake3
     has **no EVM precompile** and no cheap, audited Solidity/Yul implementation in
     wide use — implementing it correctly on-chain is itself a serious undertaking.
   - `Keccak256` is a native EVM precompile (it's literally what `keccak256(...)`
     compiles to) and is exactly what Ethereum-targeted STARK systems use instead.
     Winterfell already supports this — the upstream Fibonacci example configures
     `HashFunction::Sha3_256` alongside `Blake3_256`/`Blake3_192` — so switching
     `zkvm-stark`'s `Hasher` type to a Keccak-family hasher is a real, bounded
     change, not a rewrite. It would need to happen *before* any on-chain
     verification work starts.
2. **Merkle authentication.** The prover commits to the trace and to the
   constraint-composition polynomial as Merkle roots; the proof includes
   authentication paths for the query positions. The verifier re-hashes each path
   up to the committed root. With Keccak as the hasher this is cheap per-node, but
   a proof has `num_queries` of these (32 in our `default_options()`), each
   `log2(trace_length * blowup_factor)` nodes deep — this is the bulk of
   verification gas cost.
3. **FRI verification.** The low-degree proof is checked in rounds: each round
   folds the polynomial by the folding factor and the verifier checks
   query-consistency between rounds via more Merkle paths, then checks the final
   remainder polynomial directly. This is algorithmically the most intricate part
   to port — it's iterative, and every step needs the *exact* field arithmetic the
   prover used.
4. **Field arithmetic.** Our field is Winterfell's 128-bit prime field
   (`winter_math::fields::f128`). EVM words are 256 bits, so a value fits, but
   every add/sub/mul must be explicitly reduced mod that specific prime — there's
   no native support for an arbitrary prime field, so this is hand-rolled
   Solidity/Yul, and it has to match the prover's field bit-for-bit or every proof
   fails to verify (or worse, verifies things it shouldn't).
5. **Out-of-domain constraint check.** The verifier evaluates the AIR's transition
   constraints itself (the same formulas as `VmAir::evaluate_transition`, ported to
   Solidity) at the out-of-domain point, and checks that against the composition
   polynomial's claimed value. This is the step that actually encodes "was this the
   right AIR" — it has to be regenerated by hand any time the AIR changes.

## Why this isn't a small addition

Every real production STARK-on-Ethereum verifier (Starknet's, RISC Zero's, SP1's)
is thousands of lines of specialized Solidity/Yul, built by teams with dedicated
cryptography engineers, and it's re-audited whenever the underlying AIR or hash
choice changes. Doing it correctly but *insecurely* (an off-by-one in the FRI
folding, a missing boundary check) doesn't fail loudly — it produces a verifier that
silently accepts invalid proofs, which is strictly worse than `AttestedVerifier`'s
explicit, documented trust assumption. This is not something to bolt on in a single
pass; it's why `UnimplementedStarkVerifier` reverts instead of stubbing something
"close enough."

## The path production systems actually take: wrap it in a SNARK

Because verifying a STARK directly on the EVM is so gas-heavy, most production
systems don't do it. Instead they:

1. Run the STARK verifier itself as a program,
2. Prove *that verifier's execution* with a SNARK (Groth16 or PLONK/Halo2) that has
   a small, fixed, cheap-to-verify proof and a real EVM precompile for the
   underlying pairing curve (`ecPairing`, EIP-197), and
3. Put only that small SNARK-verification call on-chain.

This is "recursion" in practice: STARK for cheap, fast, transparent-setup proving of
the actual computation; a thin SNARK wrapper only for the part that has to run on
Ethereum. It trades a large one-time engineering cost (building the wrapper circuit)
for a small, constant per-proof on-chain verification cost — the opposite trade-off
from porting the full STARK verifier to Solidity.

## What would actually be worth building next, in order

1. Switch `zkvm-stark`'s hasher from `Blake3_256` to a Keccak/SHA3-family hasher —
   real, scoped, testable today (Winterfell already supports it).
2. A single native Rust reference verifier that mimics exactly what an on-chain
   verifier would need to do (recompute transcript, check one Merkle path, check
   one FRI round) — as a *test*, not a contract, to pin down the exact algorithm
   before writing any Solidity/Yul.
3. Only after 1–2: consider either a from-scratch Solidity/Yul STARK verifier (large,
   specialized, needs external audit) or a SNARK-wrapping approach (needs a
   separate proving system and its own trusted-setup / transparency trade-offs).

None of this is started. `AttestedVerifier` is the honest stand-in until it is.
